You are a senior full-stack product engineer and Arabic RTL interface designer. Build a complete, clean, maintainable version of Rahhala (رَحّالَة), an Arabic university class hub. Deliver working application code, not a landing page or a static visual mockup.

Rahhala puts study resources, class discussions, announcements, members and a shared study meeting in one place. Primary users are Arabic-speaking university students, with three roles: member, admin and owner.

Use Arabic for every user-facing label, validation message, empty state, confirmation and notification. Use friendly, restrained Egyptian Arabic for helper copy. Keep code identifiers in English. Set document language to Arabic and overall direction to RTL. Explicitly use LTR direction for usernames, email addresses, URLs, filenames and numeric entry when appropriate. Mixed Arabic/Latin text must remain readable.

Brand name: رَحّالَة

Do not add AI chat, payments, subscriptions, grades, attendance, exam dates, a social feed, private messaging or unrelated features. This is a focused class hub.

- Password resets revoke all sessions for the target user. A self-service password change requires the current password and must invalidate stale sessions, retaining or reissuing only the current session deliberately.
- On unauthorized/expired responses clear the local authenticated state and return to login with an understandable message.

9. UPLOADS, AUDIO AND DOWNLOADS

Support common safe image formats, PDF, browser-recorded audio, supported common audio formats and actual Office documents such as DOCX, PPTX and XLSX. Do not accept arbitrary executables or mislabeled archives as Office documents.

- Maximum ordinary upload: 15,000,000 bytes.
- Maximum voice upload: 12,000,000 bytes.
- Detect real content type from file content and validate structure where needed, not only extension or browser MIME.
- Validate supported Office container structure and return the exact Office MIME type; a PPTX must not be served merely as application/zip.
- Sanitize filenames and preserve valid Arabic filenames with correct response encoding.
- Upload ownership and attachment binding must be enforced. Users cannot attach another person's private upload by guessing its key. Only approved users can upload.
- For images, provide sensible client-side resizing/compression, around a 1,600 px longest side for chat and smaller appropriate avatars, while preserving orientation and usability.
- Render images inline in chat. Clicking opens a full-screen image viewer with close and تحميل actions, caption and safe escape/back behavior.
- Render other files as clear cards with type, filename, size and download action.
- Voice recording uses microphone permission, a visible timer, cancel and send controls. Stop media tracks after recording or cancellation. Maximum duration 15 minutes. Clearly indicate when the duration cap stops/sends the recording. Denied permission, unsupported browser and interrupted upload need usable errors.
- Audio messages have play/pause, progress/duration and no unexpected autoplay.

Download reliability is a required clean-build improvement. Do not reproduce a known failure where an error response gets saved with a PDF/PPTX filename:
- Obtain fresh authorized asset access immediately before use.
- Check HTTP success, allowed content type, expected size and complete body before saving a Blob.
- Never download a JSON/HTML error page as if it were the requested file.
- Expired access can be refreshed once safely, then show an explicit retry state.
- Use correct Content-Type, Content-Disposition and Content-Length where known, and private cache policy appropriate to protected files.
- Support a visible حفظ الملف fallback for browsers that block automatic downloads.
- Enforce timeout/cancellation and report incomplete transfers.
- Test downloaded PDF/Office bytes by parsing the actual result, not just checking the response code.

All attachment access must be authenticated or use short-lived user-scoped access links that still enforce approval, visibility and history rules. Never expose permanent public attachment URLs. Expiring links should refresh without breaking old messages. Deleting a message or revoking access must invalidate future access. Storage may use an object store or ordered chunks, but reassembly must verify complete sequence and expected byte length.
